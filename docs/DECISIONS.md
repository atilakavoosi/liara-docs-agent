# لاگ تصمیم‌های معماری (ADR)

فایل append-only. ورودی‌های قبلی هرگز پاک یا بازنویسی نمی‌شن؛ اگه تصمیمی
عوض شد، یک ADR جدید اضافه می‌شه که ADR قبلی رو نقض می‌کنه.

---

## ADR-001: نسخه‌ی AI SDK — ۱۴۰۵/۰۵/۲۹ (2026-08-20)

**Context:** باید یک نسخه از Vercel AI SDK انتخاب کنیم. نمونه‌های رسمی خود لیارا
روی `ai@4.3.16` موندن، ولی نسخه‌ی latest روی npm الان `ai@7.0.70` ـه.

**Options:**
- `ai@4` — هم‌راستا با نمونه‌های لیارا، ولی نوامبر ۲۰۲۴ و سه major عقب.
- `ai@6.0.259` — دسامبر ۲۰۲۵، پایدار، پیش از knowledge cutoff دستیار.
- `ai@7.0.70` — جدیدترین، ولی انتشارش ۲۰۲۶-۰۶-۲۵ یعنی بعد از cutoff.

**Decision:** `ai@6` به‌همراه `@ai-sdk/openai@3` و `@ai-sdk/react@3`.

**Consequences:** علیه APIای کد می‌زنیم که واقعاً می‌شناسیمش، به‌جای حدس زدن
سطح API نسخه‌ی ۷. چون لیارا صرفاً یک endpoint سازگار با OpenAI ـه، نسخه‌ی SDK
هیچ وابستگی‌ای به سمت لیارا نداره. هزینه: از قابلیت‌های احتمالی v7 محرومیم.

## ADR-002: نسخه‌ی Next.js — ۱۴۰۵/۰۵/۲۹ (2026-08-20)

**Context:** پلن اولیه Next 15 بود تا از ناسازگاری احتمالی با build پلتفرم
Next لیارا دوری کنیم. ولی `create-next-app@15` با **۳ آسیب‌پذیری high**
(postcss و sharp) نصب شد که فقط با ارتقا به Next 16 برطرف می‌شن.

**Options:**
- موندن روی Next 15 و توجیه آسیب‌پذیری‌ها در SECURITY.md.
- ارتقا به Next 16 و پذیرفتن ریسک ناسازگاری با build لیارا.

**Decision:** ارتقا به Next 16. آزمایش این ریسک وقتی اپ خالیه تقریباً رایگانه؛
اگه build لیارا شکست بخوره، برگشت به ۱۵ صفر کار از دست رفته داره. ضمناً
معیار امنیت ۵۰ امتیازه و `npm audit` تمیز بخشی از چک‌لیست تحویله.

**Consequences:** `npm audit` الان `found 0 vulnerabilities` می‌ده. build محلی
تأیید شد. باید روی خود لیارا هم تأیید بشه — اگه شکست، این ADR با ADR جدید نقض می‌شه.

## ADR-003: ایندکس استاتیک به‌جای دیتابیس برداری — ۱۴۰۵/۰۵/۲۹ (2026-08-20)

**Context:** به وکتوراستور برای ۱۱۴۲ سند مستندات نیاز داریم. لیارا Postgres
با افزونه‌ی pgvector ارائه می‌ده.

**Options:**
- Postgres + pgvector روی لیارا — «استفاده از زیرساخت لیارا» رو پررنگ‌تر می‌کنه.
- ایندکس استاتیک کامیت‌شده در ریپو، لودشده در حافظه موقع boot.

**Decision:** ایندکس استاتیک. کورپوس **۵.۴ مگابایت / ~۲۰۰۰ chunk** ـه که
تقریباً ۱۲ مگابایت بردار می‌شه — کاملاً در حد حافظه‌ی یک کانتینر معمولی.

**Consequences:** صفر هزینه‌ی دیتابیس، صفر لتنسی شبکه در بازیابی، دیپلوی
به‌مراتب ساده‌تر، و هزینه‌ی embedding فقط یک‌بار پرداخت می‌شه نه در هر دیپلوی.
در عوض: به‌روزرسانی مستندات نیاز به اجرای دوباره‌ی ingest و کامیت داره — که
برای یک هکاتون درسته، ولی در محیط واقعی باید به cron یا pgvector مهاجرت کنه.
این محدودیت صادقانه در README و ARCHITECTURE ذکر می‌شه.

## ADR-004: بازیابی هیبرید به‌جای برداری صرف — ۱۴۰۵/۰۵/۲۹ (2026-08-20)

**Context:** بازیابی برداری روی متن فنی فارسی ضعیف عمل می‌کنه. کاربر دنبال
`ECONNRESET`، اسم دقیق فیلد `nodeVersion`، یا نام سرویس می‌گرده — اینها
تطبیق واژگانی دقیق می‌خوان، نه شباهت معنایی.

**Options:** فقط برداری · فقط BM25 · هیبرید با ادغام رتبه.

**Decision:** BM25 + برداری، ادغام با RRF، سپس rerank با مدل ارزان روی top-20.
نرمال‌سازی فارسی (`ي→ی`، `ك→ک`، ارقام، نیم‌فاصله، اعراب) پیش‌نیاز غیرقابل‌حذف
سمت BM25 ـه.

**Consequences:** پیچیدگی بیشتر و یک فراخوانی مدل اضافه در هر کوئری. در عوض
مستقیماً روی سنگین‌ترین معیار داوری (۸۰ امتیاز کیفیت پاسخ) اثر می‌ذاره. با
`scripts/eval.ts` عددی سنجیده می‌شه تا این ادعا قابل اثبات باشه.

## ADR-005: فراخوانی صریح chat completions به‌جای Responses API — 2026-08-20

**Context:** موقع نوشتن `lib/ai/provider.ts` معلوم شد در
`@ai-sdk/openai@3`، فراخوانی مستقیم provider یعنی `provider(modelId)` به
**Responses API** اوپن‌ای‌آی مسیر می‌ده، نه به `/chat/completions`.
نمونه‌کدهای رسمی لیارا دقیقاً همین الگوی مستقیم رو نشون می‌دن، ولی اون‌ها
روی AI SDK v4 نوشته شدن که پیش‌فرضش chat completions بود.

**Options:**
- کپی کردن الگوی نمونه‌های لیارا و امید به اینکه Responses API پشتیبانی بشه.
- صدا زدن صریح `provider.chat(modelId)`.

**Decision:** همه‌جا صریح `.chat()`.

**Consequences:** سرویس‌های سازگار با OpenAI تقریباً همیشه فقط
`/chat/completions` رو پیاده می‌کنن. اگه الگوی نمونه‌ها رو کپی می‌کردیم،
احتمالاً موقع اولین فراخوانی واقعی با ۴۰۴ یا خطای ناشناخته روبه‌رو
می‌شدیم — دقیقاً همون نوع باگی که در ساعت آخر هکاتون گران تموم می‌شه.
هزینه: اگه لیارا بعداً Responses API اضافه کنه، از قابلیت‌هاش استفاده
نمی‌کنیم مگه اینکه این تصمیم بازبینی بشه.

**تأیید نشده:** این استنتاج از روی تایپ‌های نصب‌شده‌ست. باید با اولین
فراخوانی واقعی به سرویس لیارا تأیید بشه.

## ADR-006: AvalAI به‌جای سرویس AI خود لیارا — 2026-08-20

**Context:** پلن اولیه فرض کرده بود از سرویس AI خود لیارا
(`ai.liara.ir`) استفاده می‌شه. آتیلا کلید API از **AvalAI**
(`https://api.avalai.ir/v1`) — یک gateway سازگار با OpenAI — در اختیار
گذاشت که از قبل آماده بود.

**Options:**
- منتظر ماندن برای ساخت سرویس AI لیارا و گرفتن کلید جداگانه.
- استفاده از کلید AvalAI که همین الان در دسترسه.

**Decision:** AvalAI. چون کد از یک OpenAI provider عمومی استفاده می‌کنه
(`lib/ai/provider.ts` با `BASE_URL`/`AI_API_KEY` پیکربندی‌پذیر)، این
سوییچ هیچ تغییر کدی جز env نمی‌خواد.

**Consequences:**
- دیپلوی همچنان **کامل روی زیرساخت PaaS لیارا** انجام می‌شه — این تصمیم
  فقط ارائه‌دهنده‌ی مدل رو عوض می‌کنه، نه محل هاست برنامه. معیار «استقرار
  روی زیرساخت لیارا» (۴۰ امتیاز) دست‌نخورده می‌مونه.
- شناسه‌ی مدل‌ها در AvalAI **بدون پیشوند provider** هستن
  (`gpt-5.6-luna`، نه `openai/gpt-5.6-luna`) — برخلاف سرویس خود لیارا.
  `.env.example` و مقادیر پیش‌فرض `lib/ai/provider.ts` مطابق این اصلاح شدن.
- اگه بعداً به سرویس AI لیارا مهاجرت کردیم، فقط `BASE_URL` و `AI_API_KEY`
  و شناسه‌ی مدل‌ها عوض می‌شن.
